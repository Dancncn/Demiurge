# 企业 Agent 内核：定位、差距与优化路线

日期：2026-10-02。目标依据：企业可用、高性能、高表现强度，可嵌入业务应用或由服务提供能力。本文是对仓库实现的评估与后续建议，不是已实现能力清单或上线承诺；本轮代码验收另见 [验收记录](OPTIMIZATION-VERIFICATION.md)。

## 判断

Demiurge 有继续发展为企业 Agent 内核的基础，当前更准确的阶段是**拥有多种桌面能力的 Agent 运行时，正在建立可靠执行边界**。Rust、多个 crate、多 Agent 和大量工具提供了工程基础，但现有证据还不足以证明服务端并发性能、复杂业务完成率或企业隔离能力。

值得投入的方向是：让宿主业务系统可以依赖它完成“读取证据 → 推理与计划 → 经授权执行 → 核验结果 → 失败恢复”，并明确每一步的身份、预算、状态和证据。核心竞争力应通过复杂任务完成质量、恢复正确性、部署集成成本及单位成功任务成本证明。桌面、角色伴侣和 Minecraft 可作为消费者与回归场景，不能决定内核的依赖方向。

公开产品文档已展示多步流程、连接器、版本管理、人工介入和业务写回等能力，因此，仅增加聊天入口或工具数量很难形成稳定差异化。这是有限一手来源支持的方向判断，不是市场规模或采购意愿证明。参见 [Copilot Studio 流程能力](https://learn.microsoft.com/en-us/microsoft-copilot-studio/flows-overview) 和 [Agentforce 动作接口](https://developer.salesforce.com/docs/ai/agentforce/guide/ascript-ref-actions.html)；其余事实、日期和 preview 限制保存在 [官方证据笔记](AGENT-MARKET-EVIDENCE.md)。

## 现有基础与真实差距

| 维度 | 已存在的实现 | 达到目标仍需补足 |
| --- | --- | --- |
| 模块边界 | common/core/framework/desktop 分层；core 可独立测试 Session/Goal 规则 | 实际 runner、模型路由、工具、权限仍大量依赖 desktop 的 AppState/AppHandle；缺少完整的无桌面执行入口 |
| 执行归属 | 固定 session/项目根的 ExecutionContext；Workflow 独立取消；回答 response_id；工具事务与确认绑定 turn | 企业租户、用户、服务账号、连接器账号和策略版本尚未成为贯穿执行的身份；不能把本地会话隔离等同于租户隔离 |
| 恢复 | Workflow 定义快照、journal、失败节点重试；重启将未完结运行标为 StaleRunning | 日志辅助续跑不是确定性恢复；会话仍异步快照，没有关闭 flush；外部写入超时后的结果不明、重复提交与补偿需要专门语义 |
| 治理 | 权限规则、执行预览、确认门、工具审计；系统凭据管理器保存 API key | 宿主 SSO/RBAC/ABAC 对接、可恢复审批、凭据代理、策略撤销、审计保留与脱敏尚未形成企业接口 |
| 集成 | Provider 适配、多模态、MCP 动态发现；当前 MCP 传输枚举为 stdio | HTTP MCP、资源授权、连接器账号隔离、业务对象权限和写后核验需要明确实现；协议接通不代表业务流程可靠 |
| 调度与性能 | 有限工具循环、子任务、模型重试/预算、流式显示和用量记录 | 主聊天为单个 busy/cancel 执行域；缺少每 run 的资源配额、租户公平队列、背压和可复现负载基线 |
| 知识与质量 | 摘要、长期记忆、Lorebook BM25/远程向量召回、工作流及自动化回归 | 角色 namespace 不等于企业知识 ACL；缺少带业务验收规则的复杂任务集、重复试验和线上质量反馈 |

核对入口：[架构约束](MODULAR-ARCHITECTURE.md)、[runner](../backend/Demiurge-desktop/src/agent/runner.rs)、[ExecutionContext](../backend/Demiurge-desktop/src/agent/execution_context.rs)、[Session Engine](../backend/Demiurge-desktop/src/agent/session_engine.rs)、[Workflow](../backend/Demiurge-desktop/src/agent/workflow_runtime.rs)、[异步保存](../backend/Demiurge-desktop/src/starter/state.rs)、[权限](../backend/Demiurge-desktop/src/permission/mod.rs)、[凭据](../backend/Demiurge-desktop/src/credentials.rs)、[MCP 契约](../backend/Demiurge-common/src/mcp.rs)、[用量](../backend/Demiurge-desktop/src/usage.rs)。

本轮优化集中收紧了消息、工具、工作流和取消的归属边界，为下一步提取内核降低了风险；它尚未完成服务化或多租户改造。最新 main 的图片/视觉路由与 Minecraft 功能也说明，多入口共享运行时必须携带明确来源和执行身份，不能依靠“当前活动会话”猜测归属。

## 建议的内核边界

沿用现有模块化单体，先以一个无桌面宿主证明边界，再决定是否需要新的 crate 或独立服务。业务宿主提供身份、任务、工具和策略；内核负责执行生命周期；桌面事件、游戏消息、系统凭据与存储均通过适配器接入。

```text
桌面 / CLI / 企业应用 / HTTP worker
                │ 任务 + 执行身份 + 策略 + 预算
                ▼
     任务状态机、调度、推理循环、工具事务、恢复
                │ 明确接口
                ▼
模型网关 / 工具执行器 / 检查点存储 / 凭据代理 / 策略裁决 / 事件输出
```

建议先明确以下领域对象，只有在具体用例需要时才添加字段：

- Task 表达业务目标、输入和验收规则；Run 表达一次有版本与预算的执行。Session 保留对话用途，不兼任所有任务状态。
- Step/Attempt 区分逻辑步骤与重试；Artifact 表达可核验的交付物及来源。失败、取消、预算耗尽、等待审批和外部结果不明应有不同状态。
- ExecutionPrincipal 固定 tenant、workspace、user/service account 和 connector account；与 run id、policy version、deadline、budget、cancel scope 一起贯穿模型、工具、日志、恢复和事件。
- 外部写操作保存幂等键、请求摘要、目标版本和回执。超时可能意味着“已经写入但回复丢失”，进入 outcome_unknown，先回查或人工处理，不能一律自动重试，也不承诺跨任意服务的 exactly-once。
- 审批绑定确切动作、目标、参数摘要、版本、执行身份与有效期。修改参数后旧批准失效；审批等待需要持久化，恢复后仍受取消、权限撤销和宿主策略约束。

已有只读子 Agent 可继续承担检索、分析和验证。业务写回设置明确的提交步骤与核验步骤，避免直接给所有子 Agent 扩大写权限。模型负责处理不确定信息，金额、对象权限、审批条件、提交幂等性等可确定规则由代码执行。相关设计原则可参考 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)，具体接口仍应由本项目的宿主用例验证。

## 按验收门禁推进

不在缺少团队规模、部署环境和业务负载的情况下承诺工期。每阶段形成可评审的交付物，通过门禁再扩大范围。

| 顺序 | 交付物 | 通过条件 |
| --- | --- | --- |
| P0：测量与契约 | Task/Run/结果协议、错误分类、事件关联；代表性任务集与当前基线 | 能区分“模型说完成”和业务结果真的完成；每次试验记录代码、模型、提示、工具版本及成本 |
| P1：无桌面执行与恢复 | 可独立构建运行的 CLI/worker；模型/工具/策略/存储接口；持久化运行记录 | 核心执行路径不依赖 desktop crate 或 AppHandle；同一任务经桌面和独立入口行为一致；强制终止后能按既定语义恢复；取消不重新激活，批准不跨任务复用 |
| P2：一个企业流程的完整接入 | 宿主身份、账号范围、业务连接器、审批、受控写回和结果回查 | 覆盖跨账号拒绝、撤权、过期审批、重复请求、写后超时与进程重启；真实测试环境留下可核验业务回执 |
| P3：并发与质量提升 | 每 run 状态与取消、有限队列、公平调度、配额/背压；负载和复杂任务报告 | 在约定负载下同时达到任务质量、恢复、延迟、成本目标；所有目标先测基线再与业务方约定 |
| P4：可运营交付 | Linux/目标部署环境验证、版本兼容/迁移、审计导出、监控告警和升级回退 | 宿主可部署、定位故障、撤销权限并安全升级；试点能提供实际完成率、人工修正量与维护成本 |

单 worker 可先采用事务型本地存储；只有多 worker 的协调要求被证明后，再引入共享数据库、租约和去重。不要先拆微服务、构建插件商店或实现大规模多 Agent 群，以免把未稳定的执行语义扩散到更多边界。

## 如何证明高性能与高表现强度

把“高表现强度”定义为：长流程、多工具、信息不完整、失败和并发负载下，仍能交付符合验收规则的结果。它不是行业标准分数，需要被下面的测试解释。

| 维度 | 记录指标 | 不能替代它的指标 |
| --- | --- | --- |
| 完成质量 | 首次验收通过率、多次运行分布、人工修正量、错误类别、证据/权限正确性 | 对话字数、工具调用数、模型自报完成 |
| 可靠执行 | 重启恢复结果、重复写入数、取消后新增副作用、跨身份拒绝、结果不明的处理 | 单次正常演示或纯 mock 成功 |
| 运行性能 | 吞吐、排队时间、任务总时长 p50/p95/p99、取消响应、每 run 内存、CPU/IO 与锁等待 | Rust 语言选择、类型检查耗时 |
| 成本效率 | 每个被验收任务的 tokens、模型/工具费用、重试和人工成本 | 单次 API 价格或平均 token 数 |

先在固定硬件、模型、数据、连接器和版本下测 1/8/32 等逐级并发，再按实际容量决定更高负载。分别报告冷启动与稳态、模型等待、外部工具等待、内核开销；真实模型质量评测与受控模型响应的调度压测分开，最后做组合验证。p99 需要足够样本与采样说明，小规模试验不输出虚假的精确尾延迟。

建议建立三组参考工作负载，用它们验收通用内核能力，而不是把产品限定在一个岗位：

1. 多源资料 → 带出处报告：核对事实、引用与缺失信息处理，测检索和长上下文表现。
2. 工单/CRM 请求 → 查询 → 拟定变更 → 人工批准 → 写回 → 回读核验：测身份、策略、恢复、幂等与外部结果不明。
3. 仓库修改 → 测试 → 可审阅交付物：测文件边界、工具失败恢复、长程执行与结果验收。

从可维护的真实案例开始，逐步扩充正常、边界和故障场景；固定保留回归集，同时保留有挑战的能力集。优先使用业务状态断言和程序检查；主观质量评分应由业务专家校准，可辅以模型评分。关键任务要重复运行，不能只报告最佳一次。此评测思路参考 [Anthropic Agent evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)；本项目目前尚无上述企业任务集结果。

有测量后，再优化共享锁与全量快照复制、上下文/召回缓存、事件合并、模型分级路由和子任务并行。每个优化同时观察完成质量和成功任务成本，防止因过度压缩上下文或选择弱模型而把延迟收益换成返工。

TS7 的已测收益属于开发效率：固定基线的类型检查约快 6.88 倍，类型检查加 Vite 有效构建耗时减少约 22.9%。这些数字不能作为 Agent 推理、工具执行或并发吞吐提升；测试基线与兼容限制见 [TS7 可行性](TS7-FEASIBILITY.md)。

## 发展前景与投入判断

建议继续投入，但将下一轮里程碑设为**可嵌入、可恢复、可观测的单实例内核 + 一个真实企业流程**。这是从项目潜力走向企业可用性的最短验证路径，也能避免过早宣称支持任意业务。

潜在使用者是已有业务系统、身份和数据治理体系，需要受控 Agent 执行能力的内部平台团队与软件集成方。可验证的差异包括多模型部署选择、可审计执行、低资源开销、可恢复流程以及清晰的宿主接口。是否形成商业价值，应由试点接入时间、任务验收率、人工干预率、部署维护成本与采用意愿决定；现有材料不能给出市场份额、收入预测或竞争壁垒已成立的结论。

当前最不应继续扩大的技术负担，是将企业运行语义绑定在桌面全局状态上。优先完成上述 P0/P1，随后由一个真实写回流程约束 P2/P3 的复杂度；桌面和 Minecraft 继续作为兼容验收入口。每项新增能力都应能说明它改善了哪个业务结果，且有可重复验证方法。
