# 企业 Agent 内核：官方证据与发展判断

检索截止：**2026-10-02，Asia/Shanghai**。范围为 Claude Cowork、Microsoft Copilot Studio、Salesforce Agentforce，以及 MCP 授权规范；共 8 项一手来源。本文记录公开文档所述能力，没有登录这些产品做端到端实测，也不提供市场规模、采用人数、价格或收益率估计。

目标定位：**企业可用、高性能、高表现强度的 Agent 内核，可被业务应用嵌入或以服务方式提供能力。** 下文的桌面与对话产品用于观察内核能力如何被上层入口消费；企业流程平台与授权规范用于提取运行、治理和集成要求。

**判断：通用工具调用、任务分解与插件接入正在趋同，Demiurge 更值得验证的价值是复杂企业工作流中的执行质量、可靠性、可治理性与运行效率。** 这些价值需要由业务系统集成和可重复评测证明，包括经授权执行、失败恢复、结果核验和执行归属。下文是有限样本支持的方向判断，不是已经证明的采购需求、商业壁垒或性能优势。

## 证据与适用边界

### 1. Claude Cowork：从回答转向完成任务与交付文件

- 来源：[Get started with Claude Cowork](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork)。访问日期：2026-10-02；页面使用 today/yesterday 等相对更新时间，本次未取得稳定的绝对发布日期。
- **事实**：官方将其定位为非编码知识工作的多步执行工具；描述了计划、子任务、并行工作、文档及研究成果交付。当前文档包括云端会话 beta，也说明访问本机文件、浏览器及电脑需桌面应用保持连接。
- **支持的推断**：多步任务和成果交付可经不同交互入口消费；对内核应考察其能否向宿主提供明确的任务状态、进度和结果，而不把某一种桌面界面当作核心价值。
- **局限/日期处理**：页面同时预告 **2026-10-06** Pro/Max 新任务改为云端、移除“仅在电脑上”选项；这是截止日之后的计划，不能写成 10 月 2 日已经完成的迁移。本文也不把云端 beta 等同于所有账户全面可用。

### 2. Claude Cowork：连接器、团队流程与可复用工作方法

- 来源：[Customize Claude Cowork — Claude Academy](https://academy.claude.com/tutorials/customize-claude-cowork)。访问日期：2026-10-02；正文未标明确切发布/更新日期。
- **事实**：连接器可接入工作系统并进行读写；企业管理员控制可用连接器及读写授权。Skills 保存可重复的工作步骤，Plugins 将连接器与 Skills 打包给团队使用。
- **支持的推断**：企业内核需要承载可复用流程和受控连接器，并允许宿主施加组织策略；插件目录规模本身不足以说明执行质量或企业集成价值。
- **局限**：教程不证明每个连接器都支持完整 CRUD，也不证明流程执行准确率、部署成本或用户留存；实际能力受具体工具与授权限制。

### 3. Copilot Studio：业务自动化需要可观察、可管理的流程

- 来源：[Agent flows overview](https://learn.microsoft.com/en-us/microsoft-copilot-studio/flows-overview)。官方最后更新：**2026-08-03**；访问日期：2026-10-02。
- **事实**：Agent flows 支持手动、事件、定时触发，组合连接器、人工介入、分支循环和 AI 动作；提供运行可见性及 solution 内的草稿、版本、导入导出能力。该页明确针对 standard harness。
- **支持的推断**：嵌入式或服务化内核应以可运行、可维护的业务流程为验收单位；定义版本、运行状态和生命周期管理是宿主企业系统需要依赖的能力。
- **局限**：官方对流程“确定性”的描述不能扩展成嵌入其中的模型输出、外部系统状态或最终业务结果永远一致；不同 harness 的能力也不能混用。

### 4. Copilot Studio：审批是流程中的等待与路由节点

- 来源：[Multistage and AI approvals in agent flows](https://learn.microsoft.com/en-us/microsoft-copilot-studio/flows-advanced-approvals)。官方最后更新：**2026-06-30**；访问日期：2026-10-02。
- **事实**：Human review 连接器可创建多阶段审批，向指定审核人发起请求并等待后续处理；可组合人工、AI 和条件分支。
- **支持的推断**：业务审批应有明确对象、责任人和继续执行条件；内核需要让宿主审批系统参与等待与恢复，并能核对批准所对应的具体执行内容。
- **局限**：此能力仍标记 **preview**，官方明确不面向生产使用。文档还列出跨环境审批、附件、ALM 和分享限制；不能把路线方向当作已经成熟的企业交付保证。

### 5. Agentforce：确定性动作与模型选择动作可以共存

- 来源：[Actions — Agent Script, Agentforce Developer Guide](https://developer.salesforce.com/docs/ai/agentforce/guide/ascript-ref-actions.html)。访问日期：2026-10-02；正文未标明确切发布/更新日期。
- **事实**：动作可以由逻辑直接调用，也可以暴露为模型选择的工具；动作具有输入、输出和执行目标，可指向 Apex、Flow 或 Prompt，并可设置执行前用户确认。
- **支持的推断**：内核应支持模型推理与受约束动作协作，以明确接口承接业务校验和提交；复杂任务的完成质量需要同时评估推理与执行环节。
- **局限**：这是一份配置与接口说明，不是动作成功率报告；可配置用户确认也不等于每个动作默认开启确认。

### 6. Agentforce Coworker：业务写回与权限边界已有具体产品形式

- 来源：[Give Users Access to Create and Update Records with Agentforce Coworker](https://developer.salesforce.com/docs/data/agentforce-coworker/guide/agentforce-coworker-allow-coworker-update-records.html)。访问日期：2026-10-02；正文未标明确切发布/更新日期。
- **事实**：Coworker 提议 CRM 记录修改，用户确认后保存，并使用当前用户的对象和字段权限；该能力限于 Salesforce CRM。官方同时说明，没有专门区分 Coworker 修改与人工修改的审计日志，沿用标准历史记录。
- **支持的推断**：内核应向宿主提供可审阅变更、业务执行身份和保存结果，并保留“哪次任务、何人批准、修改了什么”的证据，支撑企业审计及故障定位。
- **局限**：不能据此宣称 Salesforce 所有 Agentforce 产品都缺乏审计能力。该页还列有必填字段、验证规则和管理员控制限制，说明“模型提议正确”与“系统允许写入”需要分开判断。

### 7. MCP 授权：协议接通不等于业务权限完整

- 来源：[Authorization — MCP 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)。规范版本日期：**2025-11-25**；访问日期：2026-10-02。这里固定引用该版本，不声称它是所有实现的唯一最新版本。
- **事实**：该授权规范针对 HTTP 传输；授权本身为可选能力，支持时规定 OAuth、受保护资源发现、目标资源和 token audience 校验等要求。STDIO 应从环境取得凭据，不直接套用该 HTTP 授权流程。
- **支持的推断**：内核连接器边界要区分调用身份、目标服务、权限范围与执行任务，才能承接企业宿主的授权约束；完成 MCP 工具发现并不能证明已实现这些要求。
- **局限**：传输授权不规定企业内部审批、业务校验、幂等提交或任务回滚；这些仍需应用和业务服务设计。本文不构成对 Demiurge MCP 实现的符合性审计。

### 8. MCP 安全实践：不能靠透传凭据替代授权边界

- 来源：[Security Best Practices — MCP 2025-11-25](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices)。官方原规范路径已重定向到此地址；按 **2025-11-25** 版本路径引用，访问日期：2026-10-02；页面未给独立修订日期。
- **事实**：官方禁止未经正确 audience 校验的 token passthrough，并解释 confused deputy、授权绕过和审计归属混淆等风险。
- **支持的推断**：企业内核承担业务写操作时，授权对象和执行身份应成为可校验、可追踪的运行时数据，使治理要求贯穿到实际动作。
- **局限**：遵循文档只能降低相关风险，不是零风险保证；本文没有执行渗透测试或验证任何特定厂商实现。

## 可用于主报告的内核发展判断

以下均为基于上述证据的工程与产品建议，尚未通过企业接入、运行基准或采购验证。“高表现强度”在本笔记中用作待验证目标：在长流程、多工具、信息不完整、失败和并发负载下仍保持可验收的任务质量。它不是已获得的跑分或行业标准术语。

| 判断 | 证据基础 | 对 Demiurge 的含义 | 需要补的验证 |
| --- | --- | --- | --- |
| 通用执行能力正在趋同 | 来源 1、2、3、5 展示工具、流程与复用能力 | 差异化落到宿主可依赖的执行语义、完成质量和运维成本 | 同一业务工作负载下的完成率、错误类型、人工修正量和接入成本 |
| 企业集成需要稳定边界 | 来源 2、3、5、7 | 以嵌入或服务调用方式承接业务输入、身份、策略和结果；上层入口可以变化 | 脱离桌面入口的调用验收、接口兼容、身份传递及宿主权限约束 |
| 审批需要绑定具体变更 | 来源 4、5、6 | 支持宿主审批流程；批准绑定任务、目标对象、参数和版本 | 审批等待与恢复、修改后旧批准失效、跨任务误用及取消后拒绝执行 |
| 可靠执行必须可核验 | 来源 3 的运行可见性、来源 6 的审计局限、来源 8 的归属风险 | 保存外部结果与执行凭证；明确重试、恢复和人工补救边界 | 网络超时但外部已提交、凭据过期、进程重启及重复提交场景 |
| 治理需贯穿宿主与执行端 | 来源 2、6、7、8 | 承接组织身份和权限，明确数据、凭据及任务隔离边界 | 跨身份/跨任务隔离、授权撤销、审计归属、部署环境和数据流向 |
| 高表现强度要用复杂任务评测证明 | 来源 3、5 支持混合流程方向；具体评测方法为工程建议 | 用带验收规则的长流程、多工具与故障场景衡量质量；保留模型和流程版本 | 代表性任务集、重复运行方差、长程错误累积、恢复后的业务一致性 |
| 高性能要与质量和负载条件一起报告 | 所引官方资料未提供可用于本项目的对照基准；此项为工程建议 | 分清模型/外部工具等待和内核自身开销，再比较资源利用与调度效率 | 固定工作负载、模型及环境下的吞吐、尾延迟、取消响应、资源占用与单位成功任务成本；先测基线，再定目标 |

建议以少量代表性企业工作流作为**内核验收工作负载**，覆盖多源读取、受约束决策、人工审批、业务系统写回与结果核验。它们用于检验通用执行与治理能力，不据此将内核限定为某个岗位的终端产品。先取得宿主接入和正常执行的基线，再加入取消、超时、重启、重复请求及并发负载；对质量、可靠性和效率分别记录结果，避免以单次演示或类型检查速度代替 Agent 运行表现。

本笔记没有给出吞吐 SLO 或上线承诺，也不认定 Demiurge 已具备表内能力。项目实现差距及建议见 [企业内核路线图](ENTERPRISE-AGENT-KERNEL-ROADMAP.md)，代码验证范围见 [验收记录](OPTIMIZATION-VERIFICATION.md)。这里支持的是“通过企业集成与可重复评测验证内核价值”的发展方向；商业壁垒仍取决于真实工作负载、部署约束、维护成本和企业采用证据。
